# Code review: anti-patterns & best practices

## Critical / high impact

### 1. **DB client creates a new connection pool on every import (serverless)**

**Where:** `src/db/index.ts`

In Next.js (and other serverless runtimes), each request or hot reload can re-execute modules. Creating `const client = postgres(...)` at top level can lead to many connection pools and exhaust DB connections.

**Best practice:** Use a singleton so the same client is reused (e.g. attach to `globalThis` in development to survive hot reload).

---

### 2. **`getNextFeatureId()` has a race condition**

**Where:** `src/db/queries/insert.ts`

Two concurrent requests can both read `max(id)`, both get the same “next” id, and one insert will fail (or overwrite). Fine for learning; in production you want DB-generated IDs.

**Best practice:** Use a `serial` / `GENERATED BY DEFAULT AS IDENTITY` column so the database assigns the id, and omit `id` from the insert. No custom “next id” logic.

---

### 3. **Unstable React list key**

**Where:** `src/app/features/page.tsx`

```tsx
key={feature.featureName + feature.createdAt}
```

- Two features with the same name and same second → duplicate key.
- You already have a unique `feature.id`; use that.

**Fix:** `key={feature.id}`

---

### 4. **No navigation from list to detail**

**Where:** `src/app/features/page.tsx`

The list doesn’t link to `/features/[id]`, so users can’t open a single feature.

**Best practice:** Use `<Link href={`/features/${feature.id}`}>` (e.g. around the feature name or a “View” link).

---

### 5. **`dotenv` in Next.js is redundant**

**Where:** `src/db/index.ts`, `drizzle.config.ts`

Next.js loads `.env`, `.env.local`, `.env.development`, etc. automatically. Calling `config({ path: ".env" })` is redundant for app code and can be misleading (e.g. `.env.local` overrides aren’t obvious).

**Best practice:** In Next.js app/routes and in code that runs under Next, rely on Next’s env loading and drop `dotenv` for that code. Keep `dotenv` only for scripts that run outside Next (e.g. `drizzle.config.ts` for `drizzle-kit` CLI).

---

### 6. **`DATABASE_URL` can be undefined at runtime**

**Where:** `src/db/index.ts`, `drizzle.config.ts`

`process.env.DATABASE_URL!` assumes the variable is always set. If it’s missing, you get a vague error from the postgres client.

**Best practice:** Validate once and throw a clear error, e.g.:

```ts
const url = process.env.DATABASE_URL;
if (!url) throw new Error("DATABASE_URL is not set");
const client = postgres(url);
```

---

## Medium impact

### 7. **Markdown stored but rendered as plain text**

**Where:** `src/app/features/[id]/page.tsx`, `src/app/features/page.tsx`

`feature.markdown` is shown in a `<div>`, so raw markdown is visible. If the intent is rich text, use a small markdown renderer (e.g. `react-markdown`) so headings, lists, and links render correctly.

---

### 8. **Create flow doesn’t redirect to the new feature**

**Where:** `src/app/features/create/actions.ts`

After creating a feature you redirect to `/features`. You could instead redirect to `/features/[id]` so the user sees the new feature immediately. That requires `createFeature` (or the action) to return the new row’s `id` (e.g. `returning()` in Drizzle).

---

### 9. **Unused Supabase packages**

**Where:** `package.json`

`@supabase/ssr` and `@supabase/supabase-js` are installed but not used in `src`; you’re using Drizzle + `postgres` only. If you’re not planning Supabase auth or API, removing them keeps the bundle and deps simpler.

---

## Lower impact / polish

### 10. **Lint script doesn’t target the project**

**Where:** `package.json`

`"lint": "eslint"` with no path often lints nothing or only the default. Use something like `"lint": "eslint ."` (and ensure `eslint.config.*` or `.eslintrc` is set up) so `pnpm run lint` actually checks your code.

---

### 11. **Default metadata**

**Where:** `src/app/layout.tsx`

`title` and `description` are still “Create Next App”. For a real or learning app, set app-specific values for better tabs and SEO.

---

### 12. **Table name casing**

**Where:** `src/db/schema.ts`

`pgTable("Features", ...)` creates a quoted identifier `"Features"` in Postgres. That’s valid and consistent with your migration. Many teams use snake_case table names (e.g. `features`) to avoid quoting; either is fine as long as migrations and schema match.

---

## What you’re doing well

- **Server Components for data:** Features list and detail pages correctly fetch in async Server Components; no unnecessary client-side fetching.
- **Server Actions for mutations:** Create flow uses a Server Action and `useActionState` for pending and errors; no API route needed.
- **Types from schema:** Using `SelectFeature` / `InsertFeature` from the schema keeps types in sync with the DB.
- **Validation in the action:** Checking required fields and trimming strings before insert.
- **`notFound()` for bad/missing id:** Dynamic route correctly uses `notFound()` for invalid or missing features.
- **Strict TypeScript:** `strict: true` in tsconfig is good for learning and catching bugs.

---

## Summary

| Priority   | Item                          | Action |
|-----------|--------------------------------|--------|
| High      | DB client singleton           | Cache client on `globalThis` in dev |
| High      | Race in getNextFeatureId      | Prefer DB identity/serial for id |
| High      | List key                      | Use `key={feature.id}` |
| High      | No link to detail             | Add `<Link>` to `/features/[id]` |
| Medium    | dotenv / DATABASE_URL         | Rely on Next env; validate URL |
| Medium    | Markdown rendering            | Add react-markdown (or similar) if desired |
| Low       | Lint script, metadata, deps   | Optional cleanup |
